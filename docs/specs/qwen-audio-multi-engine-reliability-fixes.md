## Problem Statement

用户启用 Qwen-Audio-TTS 并将默认模型切换为 `qwen-audio-3.0-tts-plus` 后，基础合成能够返回音频，但当前未提交实现同时引入了多项跨 Engine Plugin 的可靠性回归：前端无法构建；共享 DashScope 实现改变了 CosyVoice 已有的请求参数、响应格式和 PCM→MP3 边界；长文本 LLM Recommendation 完成后 Task 仍保持 pending，导致相同内容再次提交时报 `already exists`；音频缓存没有隔离 Engine Plugin、模型和 instruction；DashScope SSE 业务错误和空音频可能被当作成功；Qwen 的 LLM Recommendation 被无条件限定为医院场景；常规日志会持久化完整用户文本。

这些问题使“生成成功”“Task 完成”“缓存命中”和“HTTP 200”不再代表同一件事，也破坏了 Voice 属于特定 TTS Engine、Engine Plugin 隐藏自身协议细节的既有领域边界。当前全仓构建失败；后端测试中 CosyVoice 的 Voice List、非流式合成和 Streaming 合成均出现回归。

## Solution

在保留 Qwen-Audio-TTS 默认使用 `qwen-audio-3.0-tts-plus` 的前提下，恢复每个 Engine Plugin 对自身协议的所有权，统一 Task 生命周期和流式响应收尾规则，建立完整且类型化的合成缓存身份，并让错误、日志和 LLM Recommendation 行为具备明确、可测试的契约。

完成后，Qwen-Audio-TTS Plus 与 CosyVoice 都应通过同一公共 TTS Engine 接口工作，但不得被迫使用相同的上游请求体或音频解码流程；前端和后端构建必须通过，所有行为测试不得依赖真实外部 TTS/LLM 服务。

## User Stories

1. As a self-hoster, I want Qwen-Audio-TTS to default to `qwen-audio-3.0-tts-plus`, so that selecting the Engine Plugin uses the intended higher-quality model without extra configuration.
2. As a self-hoster, I want an explicit environment override to remain authoritative, so that I can choose another supported Qwen model when needed.
3. As a user, I want the Qwen Voice dropdown to contain only Voices supported by the configured Qwen model, so that synthesis requests are valid.
4. As a CosyVoice user, I want existing non-streaming synthesis to keep working, so that adding Qwen support does not regress another Engine Plugin.
5. As a CosyVoice user, I want Streaming PCM to continue being converted to MP3 inside the Engine Plugin, so that upper layers receive the format promised by the common interface.
6. As a user, I want every successful Streaming generation to finish its Task, so that I can submit the same text again.
7. As a user, I want every failed or cancelled Streaming generation to leave pending state, so that a stale Task cannot block later work indefinitely.
8. As a user, I want a duplicate request that is genuinely still running to receive a clear conflict response, so that the UI can explain what happened instead of showing an internal-server error.
9. As a user, I want different TTS Engines to have isolated cache entries, so that selecting one Engine Plugin never returns audio generated by another.
10. As a Qwen user, I want different instruction values to have isolated cache entries, so that dialect, emotion and speaking style are respected.
11. As a self-hoster, I want model and output-format changes to invalidate incompatible cache entries, so that configuration changes cannot serve stale audio.
12. As a user, I want an upstream DashScope business error to surface as a failed request, so that an empty or invalid audio file is never presented as success.
13. As a user, I want a zero-byte synthesis result to be treated as an error, so that playback failures are diagnosed at generation time.
14. As a content creator, I want Qwen LLM Recommendation to work for novels, advertisements, narration and conversations, so that non-medical content is not assigned doctor/patient behavior.
15. As a medical-content user, I want medical tone and roles to be inferred from my input, so that domain-specific behavior remains available without becoming a global default.
16. As a privacy-conscious user, I want routine production logs to exclude my full text and generated segment content, so that sensitive material is not persisted unexpectedly.
17. As an operator, I want logs to retain safe diagnostic metadata, so that I can troubleshoot Engine Plugin, duration, byte count, segment count and request failures without exposing content.
18. As a frontend user, I want subtitle availability to update correctly when I switch Engine Plugins, so that unsupported controls are hidden without breaking the build.
19. As a developer, I want Streaming and non-streaming LLM Recommendation to share Voice resolution behavior, so that the two paths cannot drift.
20. As a maintainer, I want builds and deterministic tests to catch these regressions before release, so that external service state does not decide whether CI passes.

## Implementation Decisions

- Keep `qwen-audio-3.0-tts-plus` as the Qwen-Audio-TTS default model. Continue honoring an explicit environment setting. The default Voice and exposed Voice List must be selected from the configured model's supported system Voices.
- Preserve the public TTS Engine contract: synthesis returns MP3-compatible `Buffer` or `Readable`, Voice discovery remains Engine-specific, and protocol details do not leak into orchestration services.
- Do not make CosyVoice and Qwen-Audio-TTS share a single rigid upstream payload/decoder. Shared DashScope code may own authentication, endpoint construction, HTTP transport and generic SSE framing, but each Engine Plugin must provide its own request builder and response/audio decoder.
- Preserve the CosyVoice boundary recorded in ADR-0001: non-streaming URL indirection and Streaming PCM→MP3 conversion remain internal to CosyVoice. Qwen-Audio-TTS may use its own Streaming MP3 response behavior.
- Introduce an explicit Task terminal-state rule. Every accepted Task must transition exactly once from pending to completed, failed or cancelled. Success is recorded only after the response input stream has ended; errors and client disconnects record the appropriate terminal state. Cleanup must be idempotent because stream end, response finish and response close can occur close together.
- Route the long-text LLM Recommendation branch through the same response-stream lifecycle helper used by other Streaming paths, or give it an equivalent completion/error/close contract. Manual piping without Task finalization is not permitted.
- Treat a duplicate deterministic Task ID as a conflict only while the original Task is actively pending. Return HTTP 409 with a stable machine-readable error. Completed, failed or cancelled Tasks must not prevent a later identical request.
- Define one typed synthesis-cache identity containing every output-affecting value: Engine Plugin identity, engine/model revision or cache namespace, text, Voice, rate, pitch, volume, instruction, output format and sample rate where applicable. Use a canonical serializer before hashing. Both Streaming and non-streaming paths use this definition.
- Extract Engine-specific Voice resolution and normalization into one shared function used by both LLM Recommendation paths. Preserve rich Voice metadata rather than reducing all Voices to strings.
- Parse DashScope SSE events into either audio data, completion, or a typed upstream error. Inspect business error codes and messages even when the HTTP status is 200. Reject malformed events when they indicate failure, propagate stream errors, and reject a completed response that produced zero audio bytes.
- Make the enhanced Qwen LLM Recommendation prompt domain-neutral. Medical examples and doctor/patient guidance may be used only when inferred from the supplied content or explicitly requested; they must not be global assumptions.
- At info level, log only safe metadata such as request correlation ID, Engine Plugin, configured model, text length or irreversible short hash, segment count, duration, retry count and audio byte count. Full prompts, source text and LLM segment JSON are excluded from routine logs. Any opt-in debug content logging must be disabled by default, clearly documented, truncated and redacted.
- Make configuration updates type-safe across all AudioConfig properties, including boolean subtitle capability. Engine changes must preserve the structured `/engines` response and update subtitle controls without string coercion.
- Update existing CosyVoice Voice assertions to the current structured Voice response only if that response shape is the intended public API. Do not weaken tests merely to accept both incompatible shapes without an API decision.
- Remove or avoid unused generated Voice datasets and source spreadsheets from the runtime bundle. If retained as documentation or generation inputs, document their purpose and ensure runtime code does not imply that clone-only Voices can be sent directly as system Voices.

## Testing Decisions

- The primary static delivery seam is the existing full-workspace build command. Backend, frontend and shared packages must all compile and build successfully.
- The primary behavioral seam is the Express HTTP API. Tests exercise engine discovery, Voice List selection, non-streaming generation, Streaming generation, repeated identical requests, active duplicate requests and error response contracts through the API rather than calling orchestration internals directly.
- HTTP behavior tests register deterministic fake Engine Plugins or mock the external transport; they must not call live Aliyun, EdgeTTS or LLM endpoints. Existing API tests are the prior art, but external network dependence must be removed.
- Add protocol-level tests at the narrow Engine Plugin seam because the public HTTP seam cannot efficiently enumerate upstream wire formats. CosyVoice tests cover its request shape, URL download, PCM Streaming conversion and MP3 output. Qwen tests cover Plus as the default, model-specific Voice List selection, request shape and Streaming MP3 decoding.
- Add DashScope SSE fixtures for successful audio, explicit business error, malformed error payload, transport error and successful completion with zero audio bytes. Error and zero-byte fixtures must reject rather than return empty success.
- Add a Task lifecycle API regression test: complete a long-text LLM Streaming request, submit the identical request again, and assert the second request is accepted. Add a concurrent duplicate case that returns 409 while the first remains pending.
- Add cache-isolation tests that vary one output-affecting field at a time. At minimum, changing Engine Plugin, configured model and instruction must invoke synthesis again rather than hit the prior cache entry.
- Add prompt tests using medical and non-medical fixtures. Non-medical input must not receive hospital, doctor or patient assumptions; medical input may receive those roles based on its content.
- Add logger capture tests showing that routine success and failure logs contain diagnostic metadata but not source text, LLM output, API keys or authorization headers.
- Add a frontend type/build regression test for Engine Plugin switching and boolean `supportsSubtitles`. The production build is the final acceptance signal.
- Keep tests deterministic and bounded. No test should require credentials, internet access, persistent user audio, or timing-sensitive sleeps.

## Out of Scope

- Voice cloning or exposing the large clone-only Qwen base Voice datasets as immediately usable system Voices.
- Automatic Engine Plugin fallback or failover.
- Real-time Engine Plugin health checks.
- Durable Task persistence across backend restarts or a distributed task queue.
- A general redesign of the frontend configuration store beyond the type safety needed for mixed property types.
- New medical-domain product behavior beyond content-driven LLM Recommendation.
- Changing the public TTS Engine return type away from MP3-compatible `Buffer | Readable`.

## Further Notes

- The current verification baseline is: full-workspace build fails because a boolean subtitle capability is passed through a string-only configuration update; backend tests pass 26 of 29 cases, with the three failures covering CosyVoice Voice List compatibility, non-streaming synthesis and Streaming synthesis.
- The observed Qwen-Audio-TTS Plus synthesis itself successfully produced audio. The `already exists` failure occurred afterward because the completed long-text LLM Task remained pending; model selection and Task lifecycle are separate concerns.
- A Task inspection endpoint currently attempts to serialize request/response objects stored in Task context and can encounter circular references. Fixing that endpoint is not required to resolve the original generation failure, but Task API responses should eventually expose a serializable public view rather than internal context.
- Acceptance requires the complete build and test suite to pass without real external service calls, with no new full-text content appearing in ordinary logs.
